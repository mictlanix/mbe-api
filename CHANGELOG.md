# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- **A pricing grid can read a page in one request** (#182). `GET /product-prices?product=` now repeats, the shape `GET /products?label=` already used. A grid page is one row per product and one column per price list, and filtering a single product meant the client fell back to one call per row — a twenty-row page was `1 + 20` requests, paid again on every scroll and every filter change. Repeated, it is two, and it still composes with `price_list` for the single-column case. `?product=1` is unchanged for every client already sending it, which is what made this preferable to embedding prices in `ProductListItem`: that would have put a join on every screen listing products, and most of them have no interest in prices
- **The page cap moved with it.** A twenty-row page against six price lists is 120 rows, and `limit` was capped at 100 — so the shape the endpoint had just been given would have come back silently truncated, which reads as "these products have no price" rather than as a missing page. `BULK_LIMIT` is one constant read by the list's `limit` and by the bulk write's body cap, deliberately: a read cap the write could not match would make a full page unwritable
- **`PUT /product-prices` upserts a page of prices in one transaction** (#183), keyed on the `UNIQUE (product, list)` the table already carries rather than on a row id. The grid's column actions — fill down, copy from the cost list, adjust every shown row by a percentage — each rewrite a whole visible page, and the per-row endpoints made that one request per cell, each independently committed. A run failing halfway left a column of prices in a state nobody asked for: the unactionable fan-out #181 was filed about, in the write direction. Either every cell in the body lands or none does, and a body naming one bad id is refused whole rather than applying its good rows first
- **Keyed on the pair, so the client stops guessing.** Choosing `POST` against `PUT /{id}` per cell required knowing whether a row existed, which the client only knew from a read that was stale by the time it wrote — and it lost that race with a 409 on what the user experienced as a plain edit. The upsert has no such branch. A repeated `(product, price_list)` in one body is a 400 rather than last-one-wins: two cells for one cell is a client bug, and resolving it silently hides it. The single-row `POST` and `PUT /{id}` are untouched — this adds a write, it does not replace them
- **`GET /products?missing_price_list=` answers "what still needs pricing?"** (#184) — the question a pricing screen exists for, and the one that had no query behind it. `GET /product-prices?price_list=N` answers the inverse, and a client cannot subtract one paged list from another paged list of 21k products. A correlated `NOT EXISTS` composes with `search` / `label` / `status` / `salable`, so "unpriced *and* salable" is one query, and `ListResponse.total` supplies the chip count for free. Zero is a real price list id in the deployment (`Costo`), so the filter tests `is not None` and never truthiness
- **`GET /products/prices/missing-facets`** gives the whole chip row in one call: `(price_list, missing_count)` for every list over the current filter set. Counted as *matching minus priced* rather than a `NOT EXISTS` per list — two indexed aggregates regardless of how many lists exist, where the per-list form is a scan each, and a list nobody has priced at all still gets a row instead of being dropped by the join. It takes no `missing_price_list` of its own, so clicking one chip does not change the numbers on the chips beside it

### Changed
- **The sales-order profit-margin validation is retired** (#185), and with it `assert_margin_in_range`, its two call sites in `add_line` and `update_line`, the `EXCLUDE_PRICE_RANGE_VALIDATION` bypass and the `price_validation_in_range_required` setting. It read `product_price.low_profit` / `high_profit` as the allowed profit-rate band for the customer's price list — a band that was per product *and* per price list, editable from no UI, holding whatever was migrated from the legacy system. mbe-ui is retiring every low/high profit field from its screens, and #185 named the order-of-operations trap that creates: leave the validation in place while the UI stops editing the fields, and the stored band keeps refusing sales-order lines with no way left to adjust it. The validation and the UI stop depending on these fields in the same release, which is the outcome that issue asked for
- **All four low/high profit fields are marked deprecated** rather than dropped: `price_list.low_profit_margin` / `high_profit_margin`, which no service, validation or projection has ever read, and `product_price.low_profit` / `high_profit`, which nothing reads now. They stay accepted on the request schemas and returned on the response schemas — a client still sending them is still obeyed, and a generated client keeps a field it compiles against — carrying a `deprecated` marker that reaches OpenAPI. The columns stay until the legacy monolith is retired. Services read them through `model_dump()` rather than by attribute, because marking a field deprecated makes Pydantic warn on attribute access, and that warning is for callers, not for the code honouring the value
- **One use survives, and it is the one that removes work from clients.** `product_price.low_profit` / `high_profit` are `NOT NULL` with no server default, so a created row still has to name them — and #183's second blocker was that the grid, which edits a price and nothing else, was forced to invent two numbers it had no business inventing. A row created without margins now takes the price list's `low_profit_margin` / `high_profit_margin`: values the data already treats as the default for that list's members, rather than a number this service made up. On an *update* an omitted margin is left alone, since there is no default to fall back to and overwriting a stored band would change what the client never mentioned

### Fixed
- **`docs/data-dictionary.md` described the four profit columns as price bounds** — "Minimum price", "Maximum price" (#185, #179). They are profit *rates* between 0 and 1, which is what `assert_margin_in_range` had already been corrected to treat them as; the dictionary still carried the reading that made 98.8% of the catalogue unsellable when the code shared it. All four now say what they are, that they are deprecated, and what still reads them
- **Six FK columns documented and two type mismatches corrected** (#179). `supplier_address`, `supplier_contact` and `supplier_bank_account` had sections saying what the table was and no column rows. `commission.comment` was documented as nullable and is `NOT NULL DEFAULT '0'` — the direction that bites, since an insert omitting it is refused rather than defaulted — and `postal_code.code` is `int(5) unsigned zerofill`, which is why `06000` reads back with its leading zero. Both mismatches are present in the checked-in dump, so neither was deployment drift: the dictionary was wrong from the start
- **`tests/unit/test_data_dictionary.py` asserts every live column is documented**, the check #179 asked for and the mirror of `test_model_schema.py`, which asserts every *mapped* column exists. It replays the migrations against the dump rather than scanning them — `ADD COLUMN` adds, `DROP COLUMN` removes, `CHANGE COLUMN` renames, `RENAME TABLE` and `DROP TABLE` move and remove tables — because without the drops every status column migration 005 retired reads as an undocumented column and the check is twenty lines of noise. The 19 legacy columns and 9 sectionless tables that remain are waived by name with a reason each, and a waiver that outlives its gap fails too, so the list can only shrink. Verified by mutation: deleting a documented column's row fails the table it belongs to, and waiving a column that is in fact documented fails `test_no_waiver_is_stale`. **Not addressed:** those 19 still need someone who knows the legacy system rather than someone reading the column type — `commissions_history.osp` and `participation varchar(19)` above all

### Fixed
- **A price list that was ever priced can be retired again** (#181, spec 015). `DELETE /price-lists/{id}` refused while anything pointed at the list, and `product_price` is the one thing that always does — so every list in real use was undeletable from a client. Clearing the blocker meant paging `GET /product-prices?price_list={id}` and issuing one `DELETE` per row: thousands of round trips for a real catalog, and a destructive client-side fan-out that half-fails into a partially-priced list. A `product_price` row is the price of a product *in that list* — unique on `(product, list)`, unreachable and meaningless once the list is gone, recording no event — so it now goes with the list. `delete_product` had already reached that conclusion for the other half of the same pair; this is the missing symmetry
- **The exempt set and the cascade set are one `frozenset`, read twice**, rather than the table being named in the `exempt=` of one call and the body of another. That is how `delete_product` does it, and it works only because the set has one member and always has: exempt a table without sweeping it and the final delete hits a foreign key violation, sweep one without exempting it and the code sits unreachable behind a 409. Deriving the cascade from `referencing_columns(PriceList)` filtered on the same set makes both mistakes unrepresentable — adding a member exempts it and sweeps it in the same edit. This is #112 in miniature, and #112 is why it is worth the loop. `tests/unit/test_price_list_service.py` asserts the identity, not the equality: two equal literals are exactly what drifts
- **Everything other than the prices still blocks**, including a relation added to the data model tomorrow that nobody has classified. The blockers are counted off the mapped foreign keys, so coverage arrives with the model rather than with an edit here, and the default for an unfamiliar relation is a 409 rather than a deletion — the refusal is recoverable, the deletion is not
- **An outstanding-orders row now carries the customer's own name** (#174), as `customer_display_name`, matching the field #173 added to `SalesOrderSummary` so the two lists agree. The row had projected `sales_order.customer_name`, the per-document *override*, which was null on all 1,840 outstanding orders in the deployment — every row rendered a dash. This list is the mirror image of #172: its *search* had always matched the customer's own name, and is in fact the code #173 copied, so a cashier could find an order by typing a name the row then refused to show. The lookup is one query keyed on the page's distinct customer ids, deliberately: the loop building each row already issues two of its own, so resolving the name per row would have made a page of twenty cost sixty round trips
- **A sales order list row now carries the customer's own name** (#172), as `customer_display_name` on `SalesOrderSummary`, joined from `customer`. The field beside it, `customer_name`, is the per-document *override* — `docs/data-dictionary.md` defines it as "Override customer name on docs" and nothing derives it from the customer row, so it is `NULL` on every sale that did not explicitly set one, which is every ordinary sale including walk-ins. A list rendering it showed a dash on every row while the customer record plainly knew the name
- **The same column was what free-text `search` matched**, so a non-numeric term was compared against a column that is null on exactly the rows a cashier is looking for. The list came back empty rather than erroring, which reads as "no such sale" rather than as a gap — a documented filter that could never match. `GET /sales-orders?search=` now ORs the customer's name in beside the override, so both a real customer and a document that overrides its name are findable. The numeric branch is untouched: digits still mean an order id or folio, never a name fragment
- **A subquery, not a join**, mirroring `customer_payment_service.outstanding_orders`, which already searched this way. The list issues a count and a page, and a join to `customer` would multiply rows on the count — making `total` disagree with the `items` beside it. The projection is a separate `attach_customer_names` keyed on the *distinct* customer ids of the page, so a page of walk-in sales fetches one row rather than twenty; it sits beside `attach_summary_totals` rather than inside it for the reason `cash_session_service.attach_relations` is separate (#141) — one computes money, one expands a foreign key — and carries its own query-count test
- **A new field rather than a fallback on `customer_name`**, because that field is writable (`SalesOrderCreate`, `SalesOrderUpdate`). Had the read side fallen back, a client reading a sale and putting it back unchanged would have written the customer's name *into* the override column, silently converting an ordinary sale into an overridden one and freezing it against a later rename; and clearing an override would have read back as the customer's name, exempting one field from the `null`-means-cleared convention #170 pins. Adding a field is also visible in a regenerated client, where redefining one carries an identical type signature and nothing fails to compile. `SalesOrderResponse` is deliberately unchanged — a client reading a single sale already fetches the full customer for price list, credit terms and addresses
- Verified by mutation rather than assumed: reverting the service leaves the search test asserting `0 == 1`, the reported symptom exactly, and drops the column back to null. The end-to-end proof runs against a real database in `tests/integration/`, but only on SQLite, so the clause the MariaDB deployment will actually run is pinned separately by compile checks — the dialect gap `tests/integration/conftest.py` documents. **Not addressed here:** `OutstandingOrderResponse.customer_name` reads the same override and shows the same dash, so that list has the display half of this bug (its search half is already correct, being what this change copied)

### Added
- **A retiring price list hands its customers to a named replacement** (#181), as `DELETE /price-lists/{id}?replacement={other_id}`. `customer.price_list` is a non-nullable FK, so every affected customer has to land on *some* tier; that is a commercial decision the API must not make silently, which is why the 409 was right and why leaving it there was not enough — the only way through it was one `PUT /customers/{id}` per customer. Naming the tier on the request that performs the retirement makes the move and the deletion one transaction, so there is no window in which customers have been moved off a list that still exists. Omitting `replacement` preserves today's behaviour exactly: refused, with `customer.price_list` and its count named
- **The move runs before the blocker check, not after.** Checking first would mean exempting `customer` when a replacement happens to be named — an exemption conditional on a request parameter, and a second place encoding the same rule. Moving first means the generic check simply finds nothing left to complain about, and it gives the right answer when a *different* blocker is also present: the customers move, the check still refuses, the whole thing rolls back, and the operator hears about the real blocker instead of the one they already handled. Verified by mutation — reordering those two lines fails three tests, two of them against a real database
- **Measured against the deployment, not asserted**: all three price lists in `mbe_dev` carry ~21,500 prices (`Costo` 21,571, `Mostrador` 21,569, `Mayoreo` 21,569), so *every* list there was undeletable and clearing one by hand was 21,569 requests. Retiring `Mayoreo` into `Mostrador` — 21,569 prices deleted, 150 customers moved — takes **0.56s** and four statements. The refusal on a list with customers now reads `Still referenced by customer.price_list (150)` and no longer names `product_price.list (21569)` beside it, which was the unactionable half. Note `Costo` sits at id **0**: a falsy primary key, so `replacement=0` has to mean that list and not "none given" — the service tests `is not None`, never truthiness
- **`GET /price-lists/{id}/delete/preview`** reports what rides on a list before the irreversible request: each relation with its count, largest first, and a total. The counterpart of the merge preview (#111) and for the same reason — a confirmation step in front of an operation that deletes thousands of rows otherwise has nothing to show. It passes no `exempt`, which is what makes it cover exactly what the retirement acts on: the union of what is swept and what blocks, by construction rather than by two lists agreeing. `total` counts records *touched* — deleted plus reassigned — so a client labelling it "will be deleted" overstates it, the same caveat the merge preview carries
- **Two new schemas rather than reusing the merge preview's identical pair.** Reusing `ProductMergePreviewResponse` would put a merge-named class in a generated client's price-list call, which is the complaint #175 was filed about; renaming it to something neutral would change the class name a shipped endpoint generates and break its current consumers. Eight lines of duplication was the cheapest of the three, and `app/schemas/product.py` says so, so the next reader does not tidy it away
- **Descriptions on the fields whose name does not carry their meaning** (#175), so the distinction survives into a generated client. `#:` comments are house style for explaining a field in the source and do not reach the OpenAPI schema — the right trade for almost every field, and the wrong one for a field a client can plausibly reach for and be wrong about with nothing failing. `customer_name` is the case it was written for: it is the per-document override, `customer_display_name` beside it is the customer's own name, both are nullable strings, the more natural-sounding name is the wrong one, and it is null on essentially every row (1,840 of 1,840 outstanding orders; 32,478 of the 32,488 sales matching the walk-in customer). A client dev picking the obvious field got `null` every time — #172 relocated from the server to the generated client. `fulfillment_intent` carries one too, for its `null`-means-never-recorded semantics. `app/schemas/__init__.py` states when a field earns a description, and `tests/unit/test_field_descriptions.py` pins the ones that have one against a rename or a tidy-up
- **User profiles — named permission templates** (spec 014). A user's permissions are 107 rows in `access_privilege`, one per `SystemObject`, so provisioning an account meant deciding 107 masks and every cashier was set up the same way as the last cashier with nothing recording that fact. A profile is a named set an administrator maintains once and copies onto users: six endpoints under `/api/v1/user-profiles` (list, create, read, update, delete, and `POST /{id}/apply/{user_id}`), plus an optional `profile_id` on `POST /users` that provisions the account in the same transaction
- **A template, not a grouping.** Applying a profile *copies* its masks into `access_privilege`; the copy is the account's own. Editing a profile afterwards reaches nobody, which is the part administrators are most likely to assume works the other way — so correcting a role means editing the profile and then re-applying it. `user.profile` records where an account was provisioned from, and it is provenance only: no authorization decision reads it, a hand-edit does not clear it, and `PUT /users/{id}` deliberately will not set it, because recording an origin without copying the permissions would assert something that was never true
- **A profile is sparse; a user is dense**, and the apply is the translation. A profile stores an entry only for an object it grants something on — absence means denied, and a zero mask is dropped so a round-trip is stable. A user keeps all 107 rows. Getting this backwards passes a naive assertion, so the integration layer counts rows rather than trusting a list: a profile granting three objects produces three entries and a user with 107, of which 104 are zero
- **Full replace, read literally** (FR-013). An apply rewrites every row the account has, so a permission the profile does not name is revoked rather than left alone — a thin profile is restrictive, not partial. That is what makes two accounts on one profile provably identical, and what makes re-applying a corrected profile an actual correction rather than a partial one. Deleting a profile users came from is refused with a 409 naming the blocking table, which needed **no new code**: `assert_not_referenced` derives its blockers from foreign-key metadata, so a plain FK on `user.profile` was the whole implementation. Retiring a role is the `status` field, not deletion
- **Name uniqueness is case-insensitive, and it had to be written rather than inherited.** The deployed collation (`utf8mb3_unicode_ci`) already makes a plain `=` case-insensitive, so a test run only against MariaDB cannot distinguish the correct implementation from the wrong one — but `tests/integration/` runs on SQLite, where `=` on `TEXT` is case-sensitive, and there the difference is a 409 that either happens or does not. Comparing on `func.lower()` makes the stated rule the enforced rule in both. Verified by mutation: removing `func.lower` fails the integration test and the source assertion, so the test is not passing for the wrong reason
- **Measured before being designed**, against the deployment database: 31 users, 3,355 `access_privilege` rows, **zero** duplicate `(user, object)` pairs, 106 objects per user minimum, and 110 distinct `object` values in use — four more than the enum defined, which is the finding below

### Fixed
- **`access_privilege` now has `UNIQUE (user, object)`** (#160, migration `015`). Both applications that read this table assumed it already did and neither degrades without it: `deps.py` uses `scalar_one_or_none()` and the legacy user-edit screen uses `SingleOrDefault`, so a duplicate pair does not resolve to one mask or the other — it makes **every request gated on that object answer 500 for that user**, an authorisation check returning neither allow nor deny. Measured before constraining: 3,355 rows, 3,355 distinct pairs, zero duplicates, so there was nothing to repair. Neither writer can create one either — the legacy controller is find-or-create per object — so the constraint records an invariant both codebases already maintained by construction. `deps.py` is deliberately **not** relaxed to `first()`: with the index in place `scalar_one_or_none()` can never raise, so it becomes an accurate assertion rather than a hazard, where `first()` would trade a loud 500 for a silent arbitrary authorisation decision
- **Adding that index broke the spec 014 profile apply, and the test caught it before the migration shipped.** `_write_privileges_from` cleared all 107 rows and re-appended them; SQLAlchemy's unit of work emits INSERTs before DELETEs within one flush, so re-inserting the same pairs collided with the rows being deleted and every apply raised `IntegrityError`. Applying migration `015` without this fix would have made `POST /user-profiles/{id}/apply/{user_id}` a 500 for every user who already had rows — which is all of them. It now updates the existing row in place and deletes only rows on objects outside the enum, which sidesteps the ordering question and is cheaper: most masks are already 0 and stay 0, so no UPDATE is issued for them at all. Found by `tests/integration/`, whose SQLite schema is built from the model metadata and therefore carries the new constraint; pinned by a test that applies three times in a row
- **`user.password` is now `varchar(255)`** (#161, migration `016`), matching the `String(255)` the model has declared since it was written. Four places were already prepared for bcrypt and the database was not: the model, its comment, `docs/specs/12-users.md`, and a `passlib[bcrypt]` dependency that is **declared and imported nowhere**. Widening is lossless — all 31 hashes are exactly 40 characters of SHA1 hex. **Correcting how this was described in spec 014**, which said a bcrypt hash "would truncate today": `sql_mode` includes `STRICT_TRANS_TABLES`, so it raised error 1406 rather than truncating. That is the better failure, and worth knowing, because silent truncation would lock an account out with nothing logged — a hash cut to 40 characters never verifies. This migration does **not** migrate the hashing; that needs its own spec, and the legacy `[StringLength (40)]` annotation has to change before both applications can read the same credential
- **`tests/unit/test_model_schema.py` now compares declared widths**, the gap that let the above hide: the name matched and the nullability matched, so no existing check could see `String(255)` against `varchar(40)`, and SQLAlchemy does not enforce length on insert. Worse, the integration layer builds from the model metadata, so *there* the column was 255 and a bcrypt hash would have fitted and passed the whole suite before failing against MariaDB — the test environment was more permissive than production, the same shape as spec 014 research R4. Measured before being written: with migrations accounted for, `user.password` was the **only** column that disagreed, so the check is precise rather than a standing source of noise
- **The same test was silently exempting 11 columns on the strength of rollback files.** `MIGRATION_SQL` globbed `*.sql`, including `*_rollback.sql`, so a column a *reverted* migration mentioned counted as "the dump's answer is stale here" and switched every check off for it — `active`, `cancelled`, `completed`, `disabled` and the rest of 005's reverted status columns. Narrowed to forward migrations only, which is what `discover()` already does; the exemption set drops from 35 columns to 24 and the suite stays green, so nothing was hiding behind them
- **`SystemObject` was missing `PRODUCTION_SITES = 107`**, behind a `# 107 absent` comment asserting an absence the data contradicted. The legacy catalog (`mbe/Model/Constants/SystemObjects.cs`) declares `ProductionSites = 107` **uncommented**, and 29 of 31 accounts already held an `access_privilege` row for it. Diffing the two catalogs: legacy has 107 active values, this enum had 106, and that was the **only** discrepancy — every other absence here (31, 70, 76–78, 104, 105) mirrors legacy's commented-out set exactly and is correct. Without the fix no profile could ever express `ProductionSites`, so full replace would have had to either wipe the 4 live grants or carve out an object indefinitely. `docs/constants.md` skipped 107 too and now has the row
- **An earlier draft of this feature would have destroyed live permission data.** The apply was first written as a blanket delete of every privilege row, justified as "healing duplicates and gaps"; the audit found zero duplicates and every user holding a complete matrix, so there was nothing to heal, and the blanket delete would have removed 88 rows on the four objects the enum omitted — 28 of them grants, across 13 of 31 accounts. It was then scoped to enum values, which was the right call while those objects were unidentified. Reading the legacy source removed the uncertainty: 70 (`SalesOrderShipments`), 104 and 105 (`SearchAllSalesOrderFrom…`) are **commented out** there, so those 59 rows are grants on features neither application has, and the blanket delete is correct after all. It removes them lazily, per account, as profiles are applied — the migration itself deletes nothing. All three versions of that decision are recorded in `specs/014-user-profiles/research.md` R3 rather than presented as if the last were the first
- **A four-query user list, caught by counting rather than by reading.** The first implementation gave `User` a `lazy='joined'` relationship to its profile, which pulled in `UserProfile`, whose own `lazy='selectin'` privileges then loaded a full mask set per profile to render a name in a list. Removing the relationship left two queries; resolving the name as a two-column projection instead of through `fk_expansion.batch_fetch` — which loads entities, and therefore their eagerly-loaded privileges — left one. Both versions returned byte-identical JSON, which is how an N+1 survives review, so the test asserts the statement count
- **The product's photo on `ProductLookupResponse` and `SalesOrderLineResponse`** (#157) — the resolved URL, the same value `photo` already carries on the product endpoints, so a client holding both renders one image from either. A point-of-sale capture grid reserves a thumbnail beside each line and neither shape it reads carried one; `products` did, but reading it from a till asks a cashier to hold the products privilege and costs a call per line on the one screen whose premise is speed
- **Both shapes, for the reason #145 needed both.** The lookup covers the row just scanned, but a resumed sale re-reads its lines through `attach_derived` and never re-runs the lookup, so the rows already captured would be exactly the ones showing an empty slot. `sales_order_detail` stores no image, so a line's photo is read through the product in **one query per line set**, never one per line; a lookup page costs no query at all, since it already holds the product rows. A product with no photo reports `null` rather than a placeholder — the client owns what an absent image looks like
- **An integration test layer that runs the API against a real database** (`tests/integration/`). Two 500s shipped in one week — #149 and #154 — and both endpoints had passing tests. `tests/api/` patches the service out, so the service never runs; `tests/unit/` mocks `db.execute`, so the SQL never reaches a database. A mocked session accepts a wrong column name without complaint, which is exactly what happened. The new layer drives the app through `httpx` with a real `AsyncSession`, real services and real SQL: **every one of the 212 endpoints** is asserted never to answer `500`, and the write paths that produced the bugs — customers, sales orders, delivery orders — are driven end to end, create through lifecycle transitions
- Verified against the bugs rather than assumed: reintroducing #149 fails **7** integration tests with the original `AttributeError`, and reintroducing #154 fails the customer-flow test as well as `test_model_schema.py`. The 212-endpoint net does **not** catch #149, because an empty body is refused by validation before the service is reached — which is why the seeded per-flow tests exist alongside it and why that limit is written down rather than left to be discovered
- **In-memory SQLite** (`aiosqlite`, a dev dependency), so *"no live database"* still holds: nothing to provision, and the suite runs on a bare checkout. The schema comes from the model metadata, so this layer cannot see a model that disagrees with the deployed schema — `tests/unit/test_model_schema.py` covers that statically, and the two compose to cover each other's blind spot. The dialect is SQLite, not MariaDB, so MySQL-specific SQL is still only exercised by compile checks and deployment. Foreign keys are enforced (`PRAGMA foreign_keys=ON`), so a bad id is refused here as it would be in production
- The schema and its baseline rows are built **once** into a template file that each test copies, rather than per test: 100 `CREATE TABLE`s and ~25 inserts 213 times over cost 40 seconds, a file copy costs microseconds. The whole suite is 1543 tests in 15 seconds, up from 1296 in 8
- **The remaining resources got the same depth** — payments, cash sessions, refunds, credit notes and delivery itineraries. Money in and money back is now driven end to end (a payment applied against an order, reversed, the balance restored; a paid sale refunded as a credit note), as is a whole trip: opened, a stop added, its lines committed, dispatched, and settled with proof and per-line outcomes. These are the flows where an assertion is only meaningful across rows — `SC-003` (ordered = delivered + returned + committed + open, on every line at every point) is a statement about a row an earlier request wrote, which a mocked session cannot even represent. Reintroducing #149 now fails **14** tests across two files rather than 7
- Three rules surfaced that no mocked test had ever exercised, and each is now pinned: **confirming a refund requires an open cash session**, applying a payment is bounded by the *payment's* unapplied balance and **not** by what the order still owes, and loading an already-committed delivery order onto a second trip is a **no-op 200** rather than a refusal — so the invariant, not the status code, is what the test asserts

### Fixed
- **`tests/unit/test_model_schema.py` now checks nullability, in both directions.** The column-name comparison it already did cannot see a misdeclared `NOT NULL` — the name was always right — so the defect below reached `main` through a test written to prevent exactly that class of bug. A model that forbids what the schema allows is caught, and so is the more dangerous reverse: a model that permits `None` on a `NOT NULL` column with no default, which writes a row the database rejects with error 1048 at whatever point in a workflow the value is absent. `NOT NULL DEFAULT` columns are excluded, since an insert omitting one succeeds. Measured before being written, as before: one column in each direction disagreed with the dump and both are explained by a migration that rewrites the column (`user`.`employee` tightened by 012, `facility`.`logo` loosened by 006), leaving the defect below as the only real one. A parse guard pins four known column specifications, because a `NOT NULL` that failed to parse would read as "nullable" and make both checks agree with anything
- **`lot_serial_tracking.expiration_date` is no longer mapped `NOT NULL`.** Found by the new integration layer on its first run: every itinerary departure failed, because posting a ledger row omits the expiration date and the model forbade that. The deployed column is `date DEFAULT NULL`, so **MariaDB was never affected** — SQLAlchemy does not enforce nullability on insert — but a schema built from these models refused the write. The cause is shadowing: `date` is a *column* on `LotSerialTracking`, so inside the class body the annotation `date | None` resolves to that column rather than to `datetime.date`, SQLAlchemy cannot read it as optional, and it falls back to `NOT NULL`. Stated explicitly now, with the reason recorded beside it. Measured across all 100 tables, this was the **only** column where the model forbids what the database allows; `user.employee` is the other disagreement with the dump and is intentional, being what migration 012 changed
- **Every customer read and write no longer returns 500** (#154). `customer_taxpayer` was mapped with a column the table does not have — `taxpayer_recipient`, where the column is `taxpayer`. It is a legacy table no migration creates, and it names its second column after itself rather than after the target's primary key, exactly as `customer_address` and `customer_contact` do; the mapping had been wrong since it was written and went unnoticed until #150 first joined through it. Confirmed against `docs/mbe_schema.sql` — `taxpayer varchar(13)`, foreign key to `taxpayer_recipient.taxpayer_recipient_id` — which agrees with the sibling convention and with the reporter's inference from the error
- **The writes were the dangerous part.** `_attach_links` runs *after* `await db.commit()` in `create_customer` and `update_customer`, so `POST /api/v1/customers` and `PUT /api/v1/customers/{id}` committed and *then* raised: a `500` that reads as "nothing happened" had in fact created or updated the customer. A retry then either trips the duplicate-code check or creates a second customer, and the row is only visible through the list, since the detail endpoint for it also failed. Anyone who hit this since #150 shipped may hold duplicates — the sweep is `SELECT customer_id, code, name FROM customer WHERE customer_id > <last known good>` against the affected database, then a check for repeated `code` values
- **Why no test caught it.** Every test of that code mocks `db.execute`, so the SQL was never handed to a database with a schema — and the unit test asserted the insert payload `{'customer': 1, 'taxpayer_recipient': ...}`, encoding the wrong column name and passing happily. A test that asserts what the code does cannot notice that what the code does is impossible. `tests/unit/test_model_schema.py` now checks **every mapped column in all 100 tables** against `docs/mbe_schema.sql` plus the `migrations/*.sql` that have run since it was dumped, and junction tables in both directions. Measured before being written: with migrations accounted for, this bug was the only unexplained mapped column in the codebase, so the check is precise rather than a standing source of noise. `docs/data-dictionary.md` now spells out the columns of all three customer junctions
- **`POST /api/v1/delivery-orders` no longer fails on every call.** Found while implementing #146. `create_from_sales_order` read the sale's own lines into `lines` — the parameter #138 had just added for the caller's requested subset — so `if lines is not None` tested a query result that is a list and never `None`, and the narrowing ran on **every** create, against `SalesOrderDetail` rows that carry no `sales_order_detail` attribute. Every create raised `AttributeError`, subset or not. The local is now `sales_lines`; the parameter is untouched. Neither existing test caught it, because the API tests patch the service out and the unit tests call `narrow_to_requested` directly — a regression test now pins that the parameter is not rebound
- **`sort` on `GET /api/v1/cash-sessions` no longer declares an OpenAPI default** (#144). The `-id` default #142 put on the schema made openapi-generator's dart-dio codegen emit `CashSessionSort? sort = -id` — it read the leading `-` of the wire value as a unary minus on a bare identifier instead of resolving which enum member carries that wire name, and the invalid Dart broke compilation of the **entire** generated client, not just the cash-sessions module: every file importing the package's barrel failed to build. The parameter is now `CashSessionSort | None = Query(None)` and `list_sessions` applies `-id` when nothing is passed, so the emitted schema is byte-for-byte the shape `status` already had and generates cleanly. **Behaviour is unchanged** — an omitted `sort` still orders newest-id-first (FR-051b), which the service test asserts directly rather than through the endpoint's signature. Special-casing dash-prefixed enum defaults in the generator was the alternative and was rejected: it puts a workaround in every consumer for a default that reads the same either way in the docs
- A regression test asserts no `default` appears on the parameter or on the `CashSessionSort` component, so re-adding one fails here rather than in a client's build

- **A sales order's lines are re-priced when its customer changes** (#131). `PUT /api/v1/sales-orders/{id}` accepted a new `customer` on a draft and then never touched the lines, so each one kept the price it was given against the *previous* customer's price list — a silent wrong total, not a visible failure. Surfaced by a point of sale, where a cashier switching the customer mid-sale is an ordinary action rather than an edge case; the legacy system re-priced. Mirrors `_change_currency`, the analogous "header value changed, lines must follow" case already in the same module, and takes **one query for the whole order** rather than one per line
- Re-pricing is **unconditional**: a line tracks whichever customer is on the order, including one whose price was typed in by hand. Preserving a hand-entered price was considered and rejected — `sales_order_detail` stores no marker distinguishing one from a listed price, so "preserve the override" could only ever have been a guess at what the previous customer's list would have charged, and a wrong guess leaves the *old* customer's price on the new customer's order. A product with no row on the new list prices at zero, exactly as `add_line` would for that customer, where confirmation's existing zero-price gate catches it
- Only ever when the customer **actually changed**. A `PUT` echoing back the customer already on the order has made no change, and without that guard a client sending the whole object back to edit a comment would wipe every negotiated price on it. `tax_rate` and `cost` are untouched: tax follows the product and cost comes from the cost price list, so neither has any bearing on which customer is buying
- **`user.employee` is required** (#127). It was nullable and nothing enforced it: measured against the deployment database on 2026-07-28, **2 of 34 active users** — `agonzalez` and `augusto`, one of them an administrator — had no employee record. Such an account authenticates normally, gets a populated UI, and is then refused by every write that authors a document; eight services already refuse an unlinked user with `422`, each with its own message, at whatever point in a workflow the user happened to reach. Migration `012_user_employee_required.sql` (+ rollback) makes the column `NOT NULL`, and `employee_id` becomes **required on user create** — breaking for any client that posted `POST /api/v1/users` without it. The invariant was policy; it is now a constraint
- The migration **links nobody**. There is no `DEFAULT` and no backfill: `0` fails the `employee_user` foreign key and the system employee (`-1`) would file a person's work under a housekeeping account, so an unlinked account has to be linked or deleted by someone who knows which employee it belongs to. Both were purged before the migration was applied anywhere, so its step 1 — the same temporary-table `CHECK` idiom as 011 — is an assertion rather than a call to action, and it stays in the file so the claim is checked at run time rather than only at planning time. Without it the `ALTER` still refuses — `sql_mode` includes `STRICT_TRANS_TABLES`, so the NULLs are not silently written as `0` — but it refuses with *"Data truncated for column 'employee' at row 1"*, which names neither the reason nor the accounts. Archiving an account is not a way out: `NOT NULL` applies to every row, active or not
- **The legacy application cannot write a NULL here**, checked before adding the constraint because a constraint the *other* writer violated would fail in production rather than in the migration. In `mbe`: `User.EmployeeId` is a non-nullable `int` carrying `[Required]`; the only write path is Edit, which assigns `Employee.Find (item.EmployeeId)`, and ActiveRecord's `Find` throws rather than returning null; and the users controller has no create action at all
- **The eight refusals are gone with it**, and `CurrentUser.employee_id` is `int` rather than `int | None` — as is `employee_id` on the user responses. The moment the column is `NOT NULL` those branches cannot execute, and this application is never run against a database that has not had its migrations applied, so keeping them would have meant an annotation admitting a `None` that the code below it can never see. Seven identical `_employee(current)` helpers are deleted and their 42 call sites read `current.employee_id` directly. `delete_facility` loses the `422` spec 013 gave it: that spec's own clarification was *"the case does not arise — every authenticated user must have an employee record"*, and the column is what now makes that true, so the check was guarding a state the schema forbids. Attribution is still never invented — there is no longer a state in which it could be, which is a stronger guarantee than a refusal
- Not relaxed, and never on offer: falling back to `SYSTEM_EMPLOYEE_ID`. Attributing a person's deletion or payment to "the system" would put a person-shaped lie in the audit trail, which is worse than either refusing or being unable to reach the state at all

> **Verified against a live database** (`mbe_dev`, left in its post-migration state with no test row): applied, column `NOT NULL`; rolled back to nullable; an unlinked user inserted, at which point the precondition failed with `CONSTRAINT chk_012_no_unlinked_users failed` and the bare `ALTER` failed with error 1265; row removed, precondition passed, `ALTER` re-applied. The `employee_user` foreign key and all 32 user rows survived both directions.

A customer registered at the counter could not be invoiced without someone later linking an RFC through a path that did not exist either

Each linked recipient comes back expanded exactly as the standalone `/taxpayer-recipients` endpoints return it, postal code and tax regime included; that expansion is not decoration but a precondition, since `TaxpayerRecipientResponse` reads both as SAT catalog objects and cannot be validated from the raw codes. `taxpayer_recipient_service.attach_relations` is now public rather than duplicated

An unknown RFC is refused by the foreign key and reaches the client as `409`, the same as an unknown address id on the same call (#107)
- **A delivery order says which sale it came from, and the list filters on it** (#147). `sales_order` now appears on `DeliveryOrderResponse` and `DeliveryOrderSummary`, and `GET /api/v1/delivery-orders?sales_order=N` answers "which deliveries belong to this sale?" in one call. Neither existed: the only link was per-line, through `DeliveryOrderLineResponse.sales_order_detail`, so resuming a part-distributed sale meant listing **every** delivery order of that customer, reading each one back for its lines because the summary has none, and keeping the ones whose lines pointed at this sale's — one request per candidate, unbounded for an active customer, and silently wrong whenever paging cut off before the relevant orders
- **Derived, not stored.** The link lives on the lines, and a child order raised by a partial delivery inherits it with its lines, so a column on the header would be a second copy that can drift; there is no migration and nothing to backfill. One query attaches it to a whole page rather than one per row. A delivery order is raised from exactly one sale, so the field is scalar — nothing in the schema *enforces* that, so a legacy row whose lines span two reports the lower id rather than failing, and the filter finds it under both. The filter includes cancelled orders: it answers what exists, and `status` is how a caller narrows that
- **A delivery order's destination can be set when it is raised** (#146) — `ship_to`, `contact`, `date` and `comment` on `DeliveryOrderCreate`, each falling back to the sale's value when omitted, so **every existing caller is unaffected**. They were settable only through a follow-up `PUT`, and since `ship_to` is otherwise inherited from the sale, every destination after the first had to be corrected that way. One sale sending goods to several addresses therefore cost two calls per destination with a partial-failure window between them: a `POST` that succeeded followed by a `PUT` that failed left a draft holding **committed quantities and pointing at the wrong address**, which the client had to detect and compensate for by cancelling what it had just created. Same class of problem #138 removed for a destination's quantities; this is its header. `PUT` keeps its job for genuine post-creation edits
- Fulfilment-type detection reads the **stated** destination rather than the sale's, when one is stated: a counter pickup is one because of where the goods end up, not because of what the sale's header happened to say (FR-005, FR-005a). An explicit `fulfillment_type` still overrides detection entirely
- **The product's unit of measurement on `ProductLookupResponse` and `SalesOrderLineResponse`** (#145) — the full SAT record (`id`, `name`, `description`, `symbol`), the same shape `unit_of_measurement` already has on the product endpoints, so a client holding both compares them field for field. A point-of-sale capture grid shows a unit per line and neither shape it reads carried one, leaving that column the only blank one on the row
- **Both shapes, not either.** The lookup alone would let a client cache the unit per product at scan time, but a resumed sale re-reads its lines through `attach_derived` and never re-runs the lookup — so the rows already captured, exactly the ones a resume exists to show, would be the blank ones. `sales_order_detail` snapshots the product's code and name and nothing else, so a line's unit is read through the product and attached in **one query per line set**, never one per line; a product whose unit has no catalog row reports `null` rather than a fabricated value
- **`GET /api/v1/sales-orders/{id}/payments`** (#134) — the payments standing against one order. Only the reverse direction existed (`/customer-payments/{id}/applications`), and `list_customer_payments` filters on customer, session, facility, date, method and verification but not on the order, so "what has been paid on this sale?" had no answer. Needed to rebuild an applied-payments panel when a partially-paid sale is resumed. Each row carries its payment's own method, reference, date and verification state, joined in one query, so a list renders without a follow-up request per application. Cancelled applications are included, for the same reason they are on the other side: a reversal stays visible. Gated by `CustomerPayments` (8) rather than the order's own privilege, because it is payment data
- **`point_sale` filter on `GET /api/v1/sales-orders`** (#136). A register's own open-sales list could previously only be approximated as `facility` + `mine=true`, which is every sale this employee has touched at this facility rather than the ones at this till
- **`requires_reference` on payment method options** (#137). Neither `PaymentMethod` nor `PaymentMethodOption` marked whether a method needs a reference or authorization number, so a client enforcing "card, transfer and cheque need one, cash does not" hardcoded that mapping against a SAT catalog this API owns and could change out from under it. Derived from the SAT code rather than stored, so it cannot drift from the catalog, and the rule lives in one place in `app/enums.py`. **A code the enum does not name defaults to not requiring one** — that direction is deliberate: an unclassified SAT code must not stop a cashier taking money until someone gets round to placing it. Nothing is *enforced* on write; this exposes the rule, it does not add a refusal
- **A per-line `tax_rate` on sales order lines** (#135) — settable on add and on update. The rate was copied from `product.tax_rate` when the line was added and could not be changed afterward by any route. The product's rate remains the default; supplying one overrides it for that line only. Bounded to `0`–`1`: it is a rate, not a percentage, and the column is `Numeric(5, 4)`
- **A contacts API** (#133) — `/api/v1/contacts`, gated by `Contacts` (12). `contact` has been a real table with real rows all along and `sales_order.contact` and `delivery_order.contact` have been accepting ids from it, but nothing produced one: a client was asked for an id it had no way to obtain or create. `mobile` defaults to `''` rather than `NULL`, matching the column. There is no `status` column on `contact`, so unlike the other catalogs the only filter is the search term
- **A customer's linked addresses and contacts** (#132, #133). `customer_address` and `customer_contact` are real junction tables that nothing exposed, so a client needing "one of this customer's addresses" as a delivery destination fell back to an unfiltered global address search, and a per-destination contact had nowhere to go but a delivery order's free-text `comment`. Both now appear on `CustomerResponse` and are set by id list on create and update, the shape `product`↔`label` already established. **Detail only** — `CustomerListItem` is untouched, so a page of customers does not cost two queries per row
- Link semantics are replace-all, but **only for a collection the caller sent**: omitting `addresses` leaves the links alone, `[]` unlinks everything. Without that distinction an ordinary `PUT` that says nothing about addresses would silently unlink every one of them
- **A delivery order can claim a named subset of a sale's undelivered quantities** (#138) — `DeliveryOrderCreate.lines`, each entry a `sales_order_detail` and a `quantity`. Omitting it keeps the original behaviour of claiming every uncovered quantity, so **every existing caller is unaffected**. This supersedes the split-by-create-then-trim procedure described under the delivery endpoints below: that forced each destination's writes to serialise, since a fresh create would otherwise claim what the previous one was supposed to keep, and put the arithmetic that must sum exactly to the ordered amount in the client. Each request is bounded by the same `_covered_quantities` figure the default path uses, so the two cannot disagree; over-claiming, naming a line twice, and naming a line of another sale are each refused with `422` saying which line and by how much
- **Facility deletion is audited.** An `incidence` row under the new `SourceType.FACILITY` records who deleted the facility and which in-transit location went with it. Staged in the same transaction as the deletes, so a facility cannot be deleted without the trace and a refused deletion leaves no orphan entry. Attribution is never invented — a user with no employee record is refused with `422` rather than logged as the system
- SQL migration `011_facility_transit_warehouses.sql` (+ rollback): adds `warehouse.in_transit`, converts the existing shared row into facility 1's own location, and backfills one per remaining facility — 19 warehouse rows became 32, 14 of them in-transit, 0 facilities without one. **Unlike 008, no id has to be captured into the environment afterwards.** The migration refuses to run if the shared location holds a nonzero balance rather than guessing which facility in-flight goods belong to; measured before writing it, that location had never been posted to, so there was nothing to redistribute
- **Expiry sweep for abandoned sales orders** (`uv run python -m app.jobs.expire_orders`, closes #118). Confirming an order reserves its stock, and the reservation is only released by cancellation, departure or a counter pickup — so an order confirmed and then abandoned held stock indefinitely, visible on the shelf but absent from availability. Nothing noticed, because on-hand stayed correct and it was *availability* that quietly fell. An order still neither paid nor delivered `UNPAID_ORDER_EXPIRY_DAYS` (default 2) after its date, **and still holding a reservation**, is now cancelled, which releases the stock through the path that already exists
- The sweep cancels through `sales_order_service.cancel_order` rather than deleting reservations directly, so an expired order is retired by the same code and the same guards as one a person cancels. A partially-paid order holds live payment applications and cannot be cancelled until they are reversed — that is somebody's decision, so the sweep **skips it, names it, and exits 1**, because a skipped order is still holding stock
- `SYSTEM_EMPLOYEE_ID` is a **constant, not a setting** (`app/core/constants.py`), fixed at **-1**. `sales_order.updater` is an enforced foreign key, so a wrong value is not a preference — it is a sweep that fails partway through with error 1452 after some orders have already been cancelled, and there is nothing a deployment gains by choosing it. The row is created at API startup if absent and by `ensure_system_employee`, so a database that never ran migration `010` still works. Attributing an automated cancellation to the salesperson would read in the audit trail as their decision. The sweep still verifies the row exists before cancelling anything, so a database in an unexpected state fails the run rather than stopping it halfway
- SQL migration `010_system_employee.sql` (+ rollback): one archived `employee` row at id **-1**. `sales_order.updater` is an enforced foreign key, so a `0` sentinel fails at write time with error 1452 — mid-sweep, after some orders are already cancelled — and employee 0 cannot be created because `NO_AUTO_VALUE_ON_ZERO` is not in `sql_mode`. A high id such as 999999 would push employee `AUTO_INCREMENT` past it and number every subsequent real employee from 1000000. A negative id is genuinely out of band: InnoDB only advances the counter for values above it. Verified — `AUTO_INCREMENT` stayed at 111 across the insert and `updater = -1` satisfied the foreign key

> **The reservation condition is load-bearing, not an optimisation.** Reservations exist only for orders confirmed after the delivery model shipped; none were backfilled. Without that condition the sweep matches every historical order never paid or delivered — measured against the live database, **1,363 orders matched the age and payment rules and not one held a reservation**. Running it would have been a mass retirement of historical documents that released nothing. Scoped as shipped, a dry run against the same data reports 0.

- **Delivery & logistics endpoints** — the delivery capability this API never had, covering `docs/specs/06-logistics.md` on the v2 status flow of `docs/specs/06a-delivery-flow-v2.md`. Two routers under `/api/v1/`: `/delivery-orders` (71, with the approval queue gated separately by 94) and `/delivery-itineraries` (87, with the pending-deliveries view gated by 91). 25 routes, three new tables, four changed ones

Enforcing it would have made `COUNTER_PICKUP` unreachable through the only route that creates a delivery order
- `fulfillment_type` may be stated when raising a delivery order, defaulting to the ship-to detection. **One sales order can split across both kinds** — part collected at the counter, the rest shipped — so the type belongs to the delivery order rather than the sale. Split by raising one order, dropping the other kind's lines while it is still a draft, then raising a second order for what remains; coverage stops the two overlapping
- Delivery orders carry an explicit `status` drawn from eleven values and an immutable `fulfillment_type`, replacing the five legacy booleans. Every transition passes through one helper that moves the status and writes a `delivery_order_event` row together, so the audit trail cannot be forgotten rather than merely being expected. **Transition legality is keyed on `(from, to, fulfillment_type)`** — approval branches by type in a single transition, so `APPROVED` is where a counter pickup rests and is never written transiently for a delivery

One signature can cover several delivery orders dropped at the same place; stops resolve independently, so a failed stop does not block the rest of the trip from closing

- Partial deliveries split their remainder into a child order at `IN_PREPARATION` naming its parent, so one order is one trip is one proof and the remainder is counted once

### Changed
- **One in-transit location per facility, replacing the single system-wide warehouse of spec 012.** Every warehouse belongs to exactly one facility, so a global in-transit row had to be parented on an arbitrary one — migration 008 used `MIN(facility_id)`. Goods dispatched from *any* facility therefore accumulated on *one* facility's books, contradicting the org chart the warehouse→facility edge exists to express. Sharper than that, as measured: the shared row sat on facility 1, which is `INACTIVE`, and `available_orders` filters on active facilities — so every other facility's in-transit stock was accruing to the one facility structurally incapable of dispatching it. Departure, acceptance and return now settle against the in-transit location of the facility that owns the **line's dispatch warehouse**, resolved in one query per trip. A trip may span facilities; each line settles against its own
- In-transit locations answer **`403 In-transit locations are managed by the system`** on GET, PUT and DELETE by id, for every role including administrator. An id naming no warehouse still answers `404`, so "forbidden" and "not found" stay distinguishable — a `404` would send a developer hunting the database for a row the API claims is absent, and a `404` that explains why the row is hidden is not a `404`. One shared helper enforces it for all three verbs, replacing the `404` block each of them repeated. `warehouse_service.get_warehouse` is deliberately left unfiltered: a service function that pretends a row does not exist is a trap for every future caller
- Creating a facility creates its in-transit location in the same transaction, so a facility never exists without one. Deleting a facility removes it, so the row the system created never blocks the delete — while inventory history on it still does, naming `lot_serial_tracking.warehouse` exactly as any other warehouse would
- Product lookup reports **`available` beside `on_hand`** per warehouse. Confirmation checks availability, not on-hand, so a salesperson shown the raw figure could see five units, promise them, and be refused because those five are reserved by other confirmed orders. `on_hand` is kept with its existing meaning — "we have five, three are spoken for" is more use than either number alone — so this is additive, not breaking
- Product lookup no longer offers the **in-transit warehouse**. It is an ordinary warehouse row so `on_hand` reports its balance with no new mechanism, which also meant it appeared in the picker as if goods already on a truck were pickable stock
- Product lookup takes **two aggregate queries** for the whole result set instead of one per product per warehouse. It was already an N+1; reporting a second figure would have doubled it. `stock_ledger.on_hand_by_warehouse` and `reserved_by_warehouse` return totals keyed by `(product, warehouse)`
- Startup checks moved from the deprecated `@app.on_event('startup')` to FastAPI's `lifespan`. Behaviour is unchanged in the respect that matters: an exception raised during startup still aborts the boot, so a misconfigured deployment fails to start rather than starting and misfiling stock. Verified both ways — a normal boot serves, and `IN_TRANSIT_WAREHOUSE_ID=0` refuses to start with the reason logged
- **Sales-order confirmation now reserves stock rather than consuming it.** Consumption moved to the delivery: `confirm_order` writes a `lot_serial_rqmt` reservation instead of an outbound ledger entry, and `cancel_order` releases the reservation instead of posting a compensating one. **The stock check moved with it** — it compares against on-hand *minus* reservations, not raw on-hand. Without that paired change confirmation would silently oversell: it no longer decrements anything, so one physical unit would satisfy an unlimited number of orders, every confirmation succeeding and the shortfall surfacing only when the truck was loaded. This supersedes two acceptance scenarios delivered with the sales cycle
- Goods now move in two steps. Departure posts an outbound entry against the line's dispatch warehouse and an inbound against a virtual in-transit warehouse; acceptance consumes from in-transit; a refusal or failure moves the goods back to the warehouse. Warehouse on-hand therefore never counts stock that is physically on a truck. **`IN_TRANSIT_WAREHOUSE_ID` must be set after running migration 008** — the API refuses to start while it is unset rather than posting entries against warehouse 0, and the id cannot be defaulted because the migration creates the row
- The in-transit warehouse is excluded from warehouse listings, so it cannot be picked on a sales order or an itinerary
- `TransactionType` gained the five legacy values it had never modelled (5–9, `InventoryTransfer` through `ProductConversion`) plus `DELIVERY_ORDER = 10` and `SALES_ORDER_RESERVATION = 11`. **A planning assumption that value 5 was free was wrong** — `docs/constants.md` allocates the whole 1–9 range and 38,411 ledger rows already use source 5. Modelling the legacy values stops the range being misread as free again
- `image_service` separates PNG normalisation from filename choice. Product images stay content-addressed; proof captures get UUID names, because deduplicating evidence would mean deleting one order's proof removed another's
- Sales orders expose per-line delivery coverage as a derived figure, and `sales_order.delivered` — dead state until now — is set once every deliverable line is delivered

> **Reservations are released per line, not per order.** A sales order reserves one row per line, so departure and counter pickup release exactly the product, warehouse and quantity that moved. Releasing by order — which is what the whole-order form does, and what departure did first — would hand back the lines that stayed behind, and those would become sellable a second time. The whole-order form survives for cancellation, where giving everything back is the point. Goods that come back from a refusal or a failed stop **re-reserve**: the ledger move is reversed and the claim is reinstated with it, so the retry and the partial delivery's child order still have stock held for them.
>
> **A confirmed sales order holds its reservation until it is cancelled, delivered or picked up — there is no expiry.** An order confirmed and then abandoned keeps its stock unavailable indefinitely, visible on the shelf but not available to promise. This matches the previous behaviour, where confirmation consumed the stock outright and only cancellation returned it; what changed is the symptom, since on-hand is now correct and availability is what quietly falls. Nothing yet reports stuck reservations.

> **Deployment note**: the lifecycle rules are enforced as clarified and are mutually exclusive by design. Only a completed, uncancelled order can be paid; only a completed **and paid** order can be refunded; a paid order is refused cancellation and directed to refund; and an order holding live payment applications cannot be cancelled until they are reversed. Because paying requires an uncancelled order, a paid order is necessarily uncancelled, so the refund path needs no separate cancellation check. A refundable order's balance is therefore always zero, which makes the legacy "apply the refund against the remaining balance" path unreachable — it is deliberately **not** implemented, and a refund never alters the order's `paid` flag or writes `balance_zeroed_time`.

- `GET /api/v1/products/merge/preview?product_id=&duplicate_id=` — how much history rides on the duplicate, so an operator sees the blast radius before committing the irreversible merge (#111). ### Fixed
- **Profit-margin validation compared a price against a rate.** `product_price.low_profit` and `high_profit` are profit *rates* — every one of the 61,855 rows in `mbe_dev` has both between 0 and 1, typically `0.000000` and `1.000000`. The new line-add check compared the raw price against them, so a ₱23.00 price failed `23 > 1`: with `price_validation_in_range_required` on by default, only 734 of 61,855 product-price rows would have passed and 98.8% of the catalogue would have been unsellable. The check is now on the derived margin `(price - cost) / price` against those rates, which is what the columns mean. A zero price is not judged there — confirmation refuses it outright and dividing by it has no meaning. Found by driving a real order through `mbe_dev`; no unit test with invented fixtures would have caught it, because the invented bounds looked like prices
- **Reading a cashier's open cash session raised on legacy data.** `cash_session.end IS NULL` is not unique in practice — two cashiers in `mbe_dev` have three and four sessions open simultaneously — and the lookups used `scalar_one_or_none()`, which raises `MultipleResultsFound`. Recording a payment as either cashier returned a 500. The three affected queries now order by `start` and take one; `open_session` still refuses to *create* a second, so the tolerance only ever applies to pre-existing rows
- `POST /api/v1/products/merge` now moves every reference the duplicate carries, not the six a hand-written list happened to name (#112). Eleven mapped foreign keys were left behind — `sales_quote_detail`, `delivery_order_detail`, `fiscal_document_detail`, `customer_refund_detail`, `purchase_request_detail`, `customer_discount`, `lot_serial_rqmt`, `supplier_return_detail`, `service_order_detail.spare_part`, `commission_product` and `commissions_history` — so deleting the duplicate hit an enforced foreign key and the whole merge rolled back with a generic conflict. A stamped CFDI keeps its own `product_code` / `product_name` snapshot, so what the document says was invoiced is unchanged — only the catalog row it points at moves, and that row is about to stop existing
- A merge moves the duplicate's *history* and discards its *configuration*. The four relations that describe how a catalog row is set up rather than what happened to it — `product_price`, `product_label`, `commission_product`, `customer_discount` — are deleted for the duplicate instead of being reassigned: the canonical is the row being kept, so its own prices, labels, commission assignment and per-customer discounts are the ones that survive. Each of the four has a unique key covering the product column, so the duplicate's rows could never all have landed on the canonical anyway; deleting them outright makes the outcome identical for every row rather than depending on which ones happened to collide. **A label or per-customer discount that existed only on the duplicate is not carried over** — set it on the canonical before merging if it should survive
- Database constraint violations return `409` instead of `500` (#107). Deleting a record that something still references is refused with the blocking `table.column` and row counts named in the error, so a client knows what to clear; the referencing tables are derived from the mapped metadata, so a new foreign key is covered as soon as its model exists. Creating or updating a warehouse, point of sale, cash drawer or vehicle with a duplicate `code` / `license_plate` is likewise `409` rather than `500`. An `IntegrityError` handler backstops anything not checked up front, returning a generic conflict — the driver message is logged, never returned, since it names tables and indexes
