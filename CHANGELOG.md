## [Unreleased]

### Fixed
- **`POST /api/v1/delivery-orders` no longer fails on every call.** Found while implementing #146. `create_from_sales_order` read the sale's own lines into `lines` — the parameter #138 had just added for the caller's requested subset — so `if lines is not None` tested a query result that is a list and never `None`, and the narrowing ran on **every** create, against `SalesOrderDetail` rows that carry no `sales_order_detail` attribute. Every create raised `AttributeError`, subset or not. The local is now `sales_lines`; the parameter is untouched. Neither existing test caught it, because the API tests patch the service out and the unit tests call `narrow_to_requested` directly — a regression test now pins that the parameter is not rebound
- **`sort` on `GET /api/v1/cash-sessions` no longer declares an OpenAPI default** (#144). The `-id` default #142 put on the schema made openapi-generator's dart-dio codegen emit `CashSessionSort? sort = -id` — it read the leading `-` of the wire value as a unary minus on a bare identifier instead of resolving which enum member carries that wire name, and the invalid Dart broke compilation of the **entire** generated client, not just the cash-sessions module: every file importing the package's barrel failed to build. The parameter is now `CashSessionSort | None = Query(None)` and `list_sessions` applies `-id` when nothing is passed, so the emitted schema is byte-for-byte the shape `status` already had and generates cleanly. **Behaviour is unchanged** — an omitted `sort` still orders newest-id-first (FR-051b), which the service test asserts directly rather than through the endpoint's signature. Special-casing dash-prefixed enum defaults in the generator was the alternative and was rejected: it puts a workaround in every consumer for a default that reads the same either way in the docs
- A regression test asserts no `default` appears on the parameter or on the `CashSessionSort` component, so re-adding one fails here rather than in a client's build

- **A sales order's lines are re-priced when its customer changes** (#131). `PUT /api/v1/sales-orders/{id}` accepted a new `customer` on a draft and then never touched the lines, so each one kept the price it was given against the *previous* customer's price list — a silent wrong total, not a visible failure. Surfaced by a point of sale, where a cashier switching the customer mid-sale is an ordinary action rather than an edge case; the legacy system re-priced. Mirrors `_change_currency`, the analogous "header value changed, lines must follow" case already in the same module, and takes **one query for the whole order** rather than one per line
- Re-pricing is **unconditional**: a line tracks whichever customer is on the order, including one whose price was typed in by hand. Preserving a hand-entered price was considered and rejected — `sales_order_detail` stores no marker distinguishing one from a listed price, so "preserve the override" could only ever have been a guess at what the previous customer's list would have charged, and a wrong guess leaves the *old* customer's price on the new customer's order. A product with no row on the new list prices at zero, exactly as `add_line` would for that customer, where confirmation's existing zero-price gate catches it
- Only ever when the customer **actually changed**. A `PUT` echoing back the customer already on the order has made no change, and without that guard a client sending the whole object back to edit a comment would wipe every negotiated price on it. `tax_rate` and `cost` are untouched: tax follows the product and cost comes from the cost price list, so neither has any bearing on which customer is buying
- **`user.employee` is required** (#127). It was nullable and nothing enforced it: measured against the deployment database on 2026-07-28, **2 of 34 active users** — `agonzalez` and `augusto`, one of them an administrator — had no employee record. Such an account authenticates normally, gets a populated UI, and is then refused by every write that authors a document; eight services already refuse an unlinked user with `422`, each with its own message, at whatever point in a workflow the user happened to reach. Migration `012_user_employee_required.sql` (+ rollback) makes the column `NOT NULL`, and `employee_id` becomes **required on user create** — breaking for any client that posted `POST /api/v1/users` without it. The invariant was policy; it is now a constraint
- The migration **links nobody**. There is no `DEFAULT` and no backfill: `0` fails the `employee_user` foreign key and the system employee (`-1`) would file a person's work under a housekeeping account, so an unlinked account has to be linked or deleted by someone who knows which employee it belongs to. Both were purged before the migration was applied anywhere, so its step 1 — the same temporary-table `CHECK` idiom as 011 — is an assertion rather than a call to action, and it stays in the file so the claim is checked at run time rather than only at planning time. Without it the `ALTER` still refuses — `sql_mode` includes `STRICT_TRANS_TABLES`, so the NULLs are not silently written as `0` — but it refuses with *"Data truncated for column 'employee' at row 1"*, which names neither the reason nor the accounts. Archiving an account is not a way out: `NOT NULL` applies to every row, active or not
- **The legacy application cannot write a NULL here**, checked before adding the constraint because a constraint the *other* writer violated would fail in production rather than in the migration. In `mbe`: `User.EmployeeId` is a non-nullable `int` carrying `[Required]`; the only write path is Edit, which assigns `Employee.Find (item.EmployeeId)`, and ActiveRecord's `Find` throws rather than returning null; and the users controller has no create action at all
- **The eight refusals are gone with it**, and `CurrentUser.employee_id` is `int` rather than `int | None` — as is `employee_id` on the user responses. The moment the column is `NOT NULL` those branches cannot execute, and this application is never run against a database that has not had its migrations applied, so keeping them would have meant an annotation admitting a `None` that the code below it can never see. Seven identical `_employee(current)` helpers are deleted and their 42 call sites read `current.employee_id` directly. `delete_facility` loses the `422` spec 013 gave it: that spec's own clarification was *"the case does not arise — every authenticated user must have an employee record"*, and the column is what now makes that true, so the check was guarding a state the schema forbids. Attribution is still never invented — there is no longer a state in which it could be, which is a stronger guarantee than a refusal
- Not relaxed, and never on offer: falling back to `SYSTEM_EMPLOYEE_ID`. Attributing a person's deletion or payment to "the system" would put a person-shaped lie in the audit trail, which is worse than either refusing or being unable to reach the state at all

> **Verified against a live database** (`mbe_dev`, left in its post-migration state with no test row): applied, column `NOT NULL`; rolled back to nullable; an unlinked user inserted, at which point the precondition failed with `CONSTRAINT chk_012_no_unlinked_users failed` and the bare `ALTER` failed with error 1265; row removed, precondition passed, `ALTER` re-applied. The `employee_user` foreign key and all 32 user rows survived both directions.

### Added
- **A delivery order says which sale it came from, and the list filters on it** (#147). `sales_order` now appears on `DeliveryOrderResponse` and `DeliveryOrderSummary`, and `GET /api/v1/delivery-orders?sales_order=N` answers "which deliveries belong to this sale?" in one call. Neither existed: the only link was per-line, through `DeliveryOrderLineResponse.sales_order_detail`, so resuming a part-distributed sale meant listing **every** delivery order of that customer, reading each one back for its lines because the summary has none, and keeping the ones whose lines pointed at this sale's — one request per candidate, unbounded for an active customer, and silently wrong whenever paging cut off before the relevant orders
- **Derived, not stored.** The link lives on the lines, and a child order raised by a partial delivery inherits it with its lines, so a column on the header would be a second copy that can drift; there is no migration and nothing to backfill. One query attaches it to a whole page rather than one per row. A delivery order is raised from exactly one sale, so the field is scalar — nothing in the schema *enforces* that, so a legacy row whose lines span two reports the lower id rather than failing, and the filter finds it under both. The filter includes cancelled orders: it answers what exists, and `status` is how a caller narrows that
- **A delivery order's destination can be set when it is raised** (#146) — `ship_to`, `contact`, `date` and `comment` on `DeliveryOrderCreate`, each falling back to the sale's value when omitted, so **every existing caller is unaffected**. They were settable only through a follow-up `PUT`, and since `ship_to` is otherwise inherited from the sale, every destination after the first had to be corrected that way. One sale sending goods to several addresses therefore cost two calls per destination with a partial-failure window between them: a `POST` that succeeded followed by a `PUT` that failed left a draft holding **committed quantities and pointing at the wrong address**, which the client had to detect and compensate for by cancelling what it had just created. Same class of problem #138 removed for a destination's quantities; this is its header. `PUT` keeps its job for genuine post-creation edits
- Fulfilment-type detection reads the **stated** destination rather than the sale's, when one is stated: a counter pickup is one because of where the goods end up, not because of what the sale's header happened to say (FR-005, FR-005a). An explicit `fulfillment_type` still overrides detection entirely
- **The product's unit of measurement on `ProductLookupResponse` and `SalesOrderLineResponse`** (#145) — the full SAT record (`id`, `name`, `description`, `symbol`), the same shape `unit_of_measurement` already has on the product endpoints, so a client holding both compares them field for field. A point-of-sale capture grid shows a unit per line and neither shape it reads carried one, leaving that column the only blank one on the row
- **Both shapes, not either.** The lookup alone would let a client cache the unit per product at scan time, but a resumed sale re-reads its lines through `attach_derived` and never re-runs the lookup — so the rows already captured, exactly the ones a resume exists to show, would be the blank ones. `sales_order_detail` snapshots the product's code and name and nothing else, so a line's unit is read through the product and attached in **one query per line set**, never one per line; a product whose unit has no catalog row reports `null` rather than a fabricated value
- **`GET /api/v1/sales-orders/{id}/payments`** (#134) — the payments standing against one order. Only the reverse direction existed (`/customer-payments/{id}/applications`), and `list_customer_payments` filters on customer, session, facility, date, method and verification but not on the order, so "what has been paid on this sale?" had no answer. Needed to rebuild an applied-payments panel when a partially-paid sale is resumed. Each row carries its payment's own method, reference, date and verification state, joined in one query, so a list renders without a follow-up request per application. Cancelled applications are included, for the same reason they are on the other side: a reversal stays visible. Gated by `CustomerPayments` (8) rather than the order's own privilege, because it is payment data
- **`point_sale` filter on `GET /api/v1/sales-orders`** (#136). A register's own open-sales list could previously only be approximated as `facility` + `mine=true`, which is every sale this employee has touched at this facility rather than the ones at this till
- **`requires_reference` on payment method options** (#137). Neither `PaymentMethod` nor `PaymentMethodOption` marked whether a method needs a reference or authorization number, so a client enforcing "card, transfer and cheque need one, cash does not" hardcoded that mapping against a SAT catalog this API owns and could change out from under it. Derived from the SAT code rather than stored, so it cannot drift from the catalog, and the rule lives in one place in `app/enums.py`. **A code the enum does not name defaults to not requiring one** — that direction is deliberate: an unclassified SAT code must not stop a cashier taking money until someone gets round to placing it. Nothing is *enforced* on write; this exposes the rule, it does not add a refusal
- **A per-line `tax_rate` on sales order lines** (#135) — settable on add and on update. The rate was copied from `product.tax_rate` when the line was added and could not be changed afterward by any route. The product's rate remains the default; supplying one overrides it for that line only. Bounded to `0`–`1`: it is a rate, not a percentage, and the column is `Numeric(5, 4)`
- **A contacts API** (#133) — `/api/v1/contacts`, gated by `Contacts` (12). `contact` has been a real table with real rows all along and `sales_order.contact` and `delivery_order.contact` have been accepting ids from it, but nothing produced one: a client was asked for an id it had no way to obtain or create. `mobile` defaults to `''` rather than `NULL`, matching the column. There is no `status` column on `contact`, so unlike the other catalogs the only filter is the search term
- **A customer's linked addresses and contacts** (#132, #133). `customer_address` and `customer_contact` are real junction tables that nothing exposed, so a client needing "one of this customer's addresses" as a delivery destination fell back to an unfiltered global address search, and a per-destination contact had nowhere to go but a delivery order's free-text `comment`. Both now appear on `CustomerResponse` and are set by id list on create and update, the shape `product`↔`label` already established. **Detail only** — `CustomerListItem` is untouched, so a page of customers does not cost two queries per row
- Link semantics are replace-all, but **only for a collection the caller sent**: omitting `addresses` leaves the links alone, `[]` unlinks everything. Without that distinction an ordinary `PUT` that says nothing about addresses would silently unlink every one of them
- **A delivery order can claim a named subset of a sale's undelivered quantities** (#138) — `DeliveryOrderCreate.lines`, each entry a `sales_order_detail` and a `quantity`. Omitting it keeps the original behaviour of claiming every uncovered quantity, so **every existing caller is unaffected**. This supersedes the split-by-create-then-trim procedure described under the delivery endpoints below: that forced each destination's writes to serialise, since a fresh create would otherwise claim what the previous one was supposed to keep, and put the arithmetic that must sum exactly to the ordered amount in the client. Each request is bounded by the same `_covered_quantities` figure the default path uses, so the two cannot disagree; over-claiming, naming a line twice, and naming a line of another sale are each refused with `422` saying which line and by how much
- **Facility deletion is audited.** An `incidence` row under the new `SourceType.FACILITY` records who deleted the facility and which in-transit location went with it. Staged in the same transaction as the deletes, so a facility cannot be deleted without the trace and a refused deletion leaves no orphan entry. Attribution is never invented — a user with no employee record is refused with `422` rather than logged as the system
- SQL migration `011_facility_transit_warehouses.sql` (+ rollback): adds `warehouse.in_transit`, converts the existing shared row into facility 1's own location, and backfills one per remaining facility — 19 warehouse rows became 32, 14 of them in-transit, 0 facilities without one. **Unlike 008, no id has to be captured into the environment afterwards.** The migration refuses to run if the shared location holds a nonzero balance rather than guessing which facility in-flight goods belong to; measured before writing it, that location had never been posted to, so there was nothing to redistribute
- **Expiry sweep for abandoned sales orders** (`uv run python -m app.jobs.expire_orders`, closes #118). Confirming an order reserves its stock, and the reservation is only released by cancellation, departure or a counter pickup — so an order confirmed and then abandoned held stock indefinitely, visible on the shelf but absent from availability. Nothing noticed, because on-hand stayed correct and it was *availability* that quietly fell. An order still neither paid nor delivered `UNPAID_ORDER_EXPIRY_DAYS` (default 2) after its date, **and still holding a reservation**, is now cancelled, which releases the stock through the path that already exists
- The sweep cancels through `sales_order_service.cancel_order` rather than deleting reservations directly, so an expired order is retired by the same code and the same guards as one a person cancels. A partially-paid order holds live payment applications and cannot be cancelled until they are reversed — that is somebody's decision, so the sweep **skips it, names it, and exits 1**, because a skipped order is still holding stock
- `SYSTEM_EMPLOYEE_ID` is a **constant, not a setting** (`app/core/constants.py`), fixed at **-1**. `sales_order.updater` is an enforced foreign key, so a wrong value is not a preference — it is a sweep that fails partway through with error 1452 after some orders have already been cancelled, and there is nothing a deployment gains by choosing it. The row is created at API startup if absent and by `ensure_system_employee`, so a database that never ran migration `010` still works. Attributing an automated cancellation to the salesperson would read in the audit trail as their decision. The sweep still verifies the row exists before cancelling anything, so a database in an unexpected state fails the run rather than stopping it halfway
- SQL migration `010_system_employee.sql` (+ rollback): one archived `employee` row at id **-1**. `sales_order.updater` is an enforced foreign key, so a `0` sentinel fails at write time with error 1452 — mid-sweep, after some orders are already cancelled — and employee 0 cannot be created because `NO_AUTO_VALUE_ON_ZERO` is not in `sql_mode`. A high id such as 999999 would push employee `AUTO_INCREMENT` past it and number every subsequent real employee from 1000000. A negative id is genuinely out of band: InnoDB only advances the counter for values above it. Verified — `AUTO_INCREMENT` stayed at 111 across the insert and `updater = -1` satisfied the foreign key

> **The reservation condition is load-bearing, not an optimisation.** Reservations exist only for orders confirmed after the delivery model shipped; none were backfilled. Without that condition the sweep matches every historical order never paid or delivered — measured against the live database, **1,363 orders matched the age and payment rules and not one held a reservation**. Running it would have been a mass retirement of historical documents that released nothing. Scoped as shipped, a dry run against the same data reports 0.

- **Delivery & logistics endpoints** — the delivery capability this API never had, covering `docs/specs/06-logistics.md` on the v2 status flow of `docs/specs/06a-delivery-flow-v2.md`. Two routers under `/api/v1/`: `/delivery-orders` (71, with the approval queue gated separately by 94) and `/delivery-itineraries` (87, with the pending-deliveries view gated by 91). 25 routes, three new tables, four changed ones
- A pickup delivery mode on the sales order does **not** block raising a delivery order. `06-logistics.md` says it must ("pickup orders cannot generate a delivery order") and the spec followed it; the data says the reverse — of 15,527 sales orders carrying `DeliveryMode.PickUp`, **15,461 have a delivery order**, because those are the counter pickups. Enforcing it would have made `COUNTER_PICKUP` unreachable through the only route that creates a delivery order
- `fulfillment_type` may be stated when raising a delivery order, defaulting to the ship-to detection. **One sales order can split across both kinds** — part collected at the counter, the rest shipped — so the type belongs to the delivery order rather than the sale. Split by raising one order, dropping the other kind's lines while it is still a draft, then raising a second order for what remains; coverage stops the two overlapping
- Delivery orders carry an explicit `status` drawn from eleven values and an immutable `fulfillment_type`, replacing the five legacy booleans. Every transition passes through one helper that moves the status and writes a `delivery_order_event` row together, so the audit trail cannot be forgotten rather than merely being expected. **Transition legality is keyed on `(from, to, fulfillment_type)`** — approval branches by type in a single transition, so `APPROVED` is where a counter pickup rests and is never written transiently for a delivery
- Five quantities per line, four of them stored: ordered, committed, delivered, returned, with `open = ordered − delivered − returned − committed`. Sent quantity lives on the itinerary line, where each trip records its own. `committed_quantity` is retained through `IN_TRANSIT` and released only at stop closure — releasing it at departure would return goods physically on the truck to the open pool and let a second dispatcher commit them
- Itineraries with stops: a trip holds a vehicle, an operator, a dispatch warehouse and departure/return timestamps, and closes stop by stop. One signature can cover several delivery orders dropped at the same place; stops resolve independently, so a failed stop does not block the rest of the trip from closing
- Proof of delivery at every terminal handover — receiver name, identification shown, timestamp, capturing employee and a stored signature or photo — for counter pickups on the same evidentiary standard as deliveries
- Partial deliveries split their remainder into a child order at `IN_PREPARATION` naming its parent, so one order is one trip is one proof and the remainder is counted once
- `DeliveryOrderStatus`, `FulfillmentType`, `ItineraryStatus`, `StopOutcome` and `ShortfallReason` enums; five delivery settings in `app/core/config.py` replacing legacy `WebConfig` values
- SQL migration `008_delivery_flow_v2.sql` (+ rollback) — see the Changed and Removed notes below

### Changed
- **One in-transit location per facility, replacing the single system-wide warehouse of spec 012.** Every warehouse belongs to exactly one facility, so a global in-transit row had to be parented on an arbitrary one — migration 008 used `MIN(facility_id)`. Goods dispatched from *any* facility therefore accumulated on *one* facility's books, contradicting the org chart the warehouse→facility edge exists to express. Sharper than that, as measured: the shared row sat on facility 1, which is `INACTIVE`, and `available_orders` filters on active facilities — so every other facility's in-transit stock was accruing to the one facility structurally incapable of dispatching it. Departure, acceptance and return now settle against the in-transit location of the facility that owns the **line's dispatch warehouse**, resolved in one query per trip. A trip may span facilities; each line settles against its own
- In-transit locations answer **`403 In-transit locations are managed by the system`** on GET, PUT and DELETE by id, for every role including administrator. An id naming no warehouse still answers `404`, so "forbidden" and "not found" stay distinguishable — a `404` would send a developer hunting the database for a row the API claims is absent, and a `404` that explains why the row is hidden is not a `404`. One shared helper enforces it for all three verbs, replacing the `404` block each of them repeated. `warehouse_service.get_warehouse` is deliberately left unfiltered: a service function that pretends a row does not exist is a trap for every future caller
- Creating a facility creates its in-transit location in the same transaction, so a facility never exists without one. Deleting a facility removes it, so the row the system created never blocks the delete — while inventory history on it still does, naming `lot_serial_tracking.warehouse` exactly as any other warehouse would
- Product lookup reports **`available` beside `on_hand`** per warehouse. Confirmation checks availability, not on-hand, so a salesperson shown the raw figure could see five units, promise them, and be refused because those five are reserved by other confirmed orders. `on_hand` is kept with its existing meaning — "we have five, three are spoken for" is more use than either number alone — so this is additive, not breaking
- Product lookup no longer offers the **in-transit warehouse**. It is an ordinary warehouse row so `on_hand` reports its balance with no new mechanism, which also meant it appeared in the picker as if goods already on a truck were pickable stock
- Product lookup takes **two aggregate queries** for the whole result set instead of one per product per warehouse. It was already an N+1; reporting a second figure would have doubled it. `stock_ledger.on_hand_by_warehouse` and `reserved_by_warehouse` return totals keyed by `(product, warehouse)`
- Startup checks moved from the deprecated `@app.on_event('startup')` to FastAPI's `lifespan`. Behaviour is unchanged in the respect that matters: an exception raised during startup still aborts the boot, so a misconfigured deployment fails to start rather than starting and misfiling stock. Verified both ways — a normal boot serves, and `IN_TRANSIT_WAREHOUSE_ID=0` refuses to start with the reason logged
- **Sales-order confirmation now reserves stock rather than consuming it.** Consumption moved to the delivery: `confirm_order` writes a `lot_serial_rqmt` reservation instead of an outbound ledger entry, and `cancel_order` releases the reservation instead of posting a compensating one. **The stock check moved with it** — it compares against on-hand *minus* reservations, not raw on-hand. Without that paired change confirmation would silently oversell: it no longer decrements anything, so one physical unit would satisfy an unlimited number of orders, every confirmation succeeding and the shortfall surfacing only when the truck was loaded. This supersedes two acceptance scenarios delivered with the sales cycle
- Goods now move in two steps. Departure posts an outbound entry against the line's dispatch warehouse and an inbound against a virtual in-transit warehouse; acceptance consumes from in-transit; a refusal or failure moves the goods back to the warehouse. Warehouse on-hand therefore never counts stock that is physically on a truck. **`IN_TRANSIT_WAREHOUSE_ID` must be set after running migration 008** — the API refuses to start while it is unset rather than posting entries against warehouse 0, and the id cannot be defaulted because the migration creates the row
- The in-transit warehouse is excluded from warehouse listings, so it cannot be picked on a sales order or an itinerary
- `TransactionType` gained the five legacy values it had never modelled (5–9, `InventoryTransfer` through `ProductConversion`) plus `DELIVERY_ORDER = 10` and `SALES_ORDER_RESERVATION = 11`. **A planning assumption that value 5 was free was wrong** — `docs/constants.md` allocates the whole 1–9 range and 38,411 ledger rows already use source 5. Modelling the legacy values stops the range being misread as free again
- `image_service` separates PNG normalisation from filename choice. Product images stay content-addressed; proof captures get UUID names, because deduplicating evidence would mean deleting one order's proof removed another's
- Sales orders expose per-line delivery coverage as a derived figure, and `sales_order.delivered` — dead state until now — is set once every deliverable line is delivered

> **Reservations are released per line, not per order.** A sales order reserves one row per line, so departure and counter pickup release exactly the product, warehouse and quantity that moved. Releasing by order — which is what the whole-order form does, and what departure did first — would hand back the lines that stayed behind, and those would become sellable a second time. The whole-order form survives for cancellation, where giving everything back is the point. Goods that come back from a refusal or a failed stop **re-reserve**: the ledger move is reversed and the claim is reinstated with it, so the retry and the partial delivery's child order still have stock held for them.
>
> **A confirmed sales order holds its reservation until it is cancelled, delivered or picked up — there is no expiry.** An order confirmed and then abandoned keeps its stock unavailable indefinitely, visible on the shelf but not available to promise. This matches the previous behaviour, where confirmation consumed the stock outright and only cancellation returned it; what changed is the symptom, since on-hand is now correct and availability is what quietly falls. Nothing yet reports stuck reservations.

### Removed
- **`IN_TRANSIT_WAREHOUSE_ID` and its startup check.** The setting existed only because migration 008's single in-transit warehouse got an id that could not be defaulted, and the API refused to boot while it was unset. There is one location per facility now, found by its flag, so there is nothing left to configure and nothing for a startup check to verify. The failure it guarded moved to the point of use, where it belongs: a dispatch from a facility with no in-transit location is refused by name with `422`, for that facility, instead of the whole deployment failing to start. A leftover `IN_TRANSIT_WAREHOUSE_ID` in a live `.env` is inert — `Settings` is `extra='ignore'`
- **`sales_order_detail.delivery`**, by migration `009` — **breaking**: the field disappears from the sales-order line request and response bodies. Written by this API, read by nothing. `docs/specs/06-logistics.md` presents it as selecting which lines a delivery order covers and spec 012 implemented that rule first, but the column was **0 on all 910,891 rows**, including the 54,741 the legacy delivery orders were actually raised from — so the rule selected nothing, and because the same predicate sat in three queries it disabled delivery-order creation, the sales-order `delivered` write-back and the derived coverage figures at once. Delivery orders are bounded by coverage instead. The column is dropped rather than left inert because a write-only field that looks authoritative invites the next reader to restore the filter, which is exactly the mistake this feature made. A sale mixing shipped and collected lines is expressed by splitting it across two delivery orders of different fulfilment types, which records what happened to the goods instead of excluding a line from delivery
- Seven columns, by migration `008`. `delivery_order` loses `completed`, `cancelled`, `confirmed`, `delivered` and `picked_up`; `deliveries_itinerary` loses `cancelled` and `completed`. Five booleans admitted 32 combinations for 11 legal states and production carried 14 distinct ones — including a row that was simultaneously cancelled, completed and picked up
- `deliveries_itinerary_detail.deliveries_itinerary` — the stop is now the sole path to the trip, so a line can no longer claim one itinerary while its stop belongs to another

> **Migration 008 is destructive.** All 26,763 existing delivery orders settle into terminal statuses: 1,059 cancelled, 3,769 delivered, 4,160 picked up, and 17,775 completed-but-undelivered rows cancelled as abandoned — the legacy application did not maintain its `delivered` flag, so treating those as live work would open the pending queue with years of stale paperwork. **Any delivery genuinely in flight at cutover must be re-raised from its sales order**, which works because cancelled delivery orders do not count as coverage. The 1,219 `serial = 0` placeholders become `NULL` and a unique index on `(facility, serial)` is added; the audit found zero duplicate folios, so no renumbering step was needed. Every one of the 3,617 itineraries settles to `CLOSED` or `CANCELLED` and **none is left `OPEN`** — a stale open row would permanently block its vehicle from receiving another itinerary. The rollback restores the schema but **cannot** restore the pre-migration completed/cancelled distribution; rolling back in production needs the backup, not just the script.

> **Verified against a live database** (`mbe_dev`): migration applied, 19 outcome assertions checked, rolled back, 9 schema assertions checked, data restored from a table-level backup, then re-applied. The reservation model applies only to sales orders confirmed after this ships — the 178,045 already-confirmed ones keep the outbound entries their confirmation posted, and no reservation is backfilled.

- **Sales cycle endpoints** — the first transactional capability in this API, covering `docs/specs/02-sales.md`. Six routers under `/api/v1/`: `/sales-orders` (7), `/sales-quotes` (30), `/customer-payments` (8), `/customer-refunds` (22), `/cash-sessions` (44, close gated by 111), `/credit-notes` (83). No new model and no column change — every table was already mapped
- Sales orders: create from configured defaults, line management snapshotting product code/name/tax/cost, minimum-quantity and profit-margin validation (bypassed by privilege 102), confirm assigning the folio and posting outbound stock, cancel posting a compensating inbound entry, currency change, and a barcode-aware product lookup (a 13-digit numeric pattern is a scan, not a search term)
- Customer payments: record, apply to an order, reverse with a **mandatory** reason, verify, reject, and the outstanding-orders search. An application is never deleted — reversing flips `cancelled` and writes an `incidence` entry naming who, when and why, so the payments editor sees the whole history rather than the live subset
- Customer refunds: open against a **paid** order pre-populated with refundable lines at quantity zero, per-line quantity capped at what is still refundable, confirm re-validating every quantity under a `FOR UPDATE` lock on the source order, and payout as cash from the open session or as a credit note at the cashier's choice
- Cash sessions: open with an opening amount, close with denomination counts, and a current-session response distinguishing **three** states — none, open-today, open-stale. A shift left open overnight needs a different remedy from having no shift, and a single falsy answer cannot express that
- Credit notes: listed with a remaining balance derived from the backing payment's non-cancelled applications. `refunded` is the amount issued and is never decremented, so there is no second balance to drift. Redemption has **no route of its own** — it is an ordinary payment application, which keeps it bounded, reversible and correctable by the code that already does those things
- `PaymentTerms`, `PaymentMethod`, `PaymentType`, `Priority`, `CashCountType`, `TransactionType` and `SourceType` enums in `app/enums.py`, values taken from `docs/constants.md`; five sales settings in `app/core/config.py` replacing legacy `WebConfig` values
- `CurrentUser` now carries `employee_id`, `point_sale_id` and `cash_drawer_id`, read from the already-loaded `User` row and its eager-loaded settings rather than the JWT — so no live session is invalidated and no re-login is forced. A user with no employee, or no point of sale, is refused up front with **distinguishable** errors instead of failing on a NOT NULL constraint
- Four shared service helpers: `totals.py` (money, quantized once at document level — rounding per line then summing drifts and would break the balance arithmetic), `documents.py` (folio assignment under a facility row lock, editability guard), `stock_ledger.py` (append-only `lot_serial_tracking`), `incidences.py` (audit entries)

> **Deployment note**: the lifecycle rules are enforced as clarified and are mutually exclusive by design. Only a completed, uncancelled order can be paid; only a completed **and paid** order can be refunded; a paid order is refused cancellation and directed to refund; and an order holding live payment applications cannot be cancelled until they are reversed. Because paying requires an uncancelled order, a paid order is necessarily uncancelled, so the refund path needs no separate cancellation check. A refundable order's balance is therefore always zero, which makes the legacy "apply the refund against the remaining balance" path unreachable — it is deliberately **not** implemented, and a refund never alters the order's `paid` flag or writes `balance_zeroed_time`.

> **Verified against a live database** (`mbe_dev`, every created row deleted afterwards): the order lifecycle end to end; the cash session lifecycle including the stale-session path; both refund payout forms, with the source order correctly staying paid; quote confirm/duplicate/convert with expired and cancelled conversions refused; credit-note redemption and its reversal restoring both balances exactly; stock on-hand falling 40 → 37 on confirm and returning to 40 on cancel with the original ledger entry intact and a reversal appended; and both concurrency invariants — two simultaneous folio assignments yielding distinct serials, and a second refund seeing only what the first left refundable.

> **Note**: all six list endpoints batch their derived figures per page rather than per row — a page of 50 costs the same query count as a page of 1, asserted by `tests/unit/test_list_query_counts.py` so a reintroduced loop fails the suite. `SystemObject.POS` (44) governs only the cash-session routes — no point-of-sale endpoints exist, by design.

- SQL migration `007_document_serial_unique.sql` (+ rollback): a unique index on `(facility, serial)` for `sales_order`, `sales_quote` and `customer_refund`, so a duplicate folio is refused by the database rather than only by application code. Two classes of pre-existing violation are corrected first, in order. `serial = 0` is the legacy application's placeholder for "not numbered", not folio zero — 4,240 rows carry it (4,065 sales quotes, 3,974 of them completed; 172 refunds; 3 orders, all from 2024 onward) and become `NULL`, which a MySQL unique index permits any number of. Then 34 rows dating 2018-2023 that genuinely share a folio are resolved by keeping the earliest document's number and moving the 21 later ones to the next free serials for their facility. **A reassigned `customer_refund` folio will no longer match a receipt printed years ago.** The `0 -> NULL` step must run before the renumber, or the 4,240 placeholder rows would be treated as duplicates and issued real folios. Verified against the live database inside a rolled-back transaction before shipping: zero duplicate groups remain on all three tables. The rollback drops the indexes only — the data corrections are not reversible
- `GET /api/v1/products/merge/preview?product_id=&duplicate_id=` — how much history rides on the duplicate, so an operator sees the blast radius before committing the irreversible merge (#111). Returns `{items: [{category, count}], total}`, counted per referencing `table.column` and sorted largest first, gated by `PRODUCTS_MERGE` (73) with `AllowRead`. The counts come from the same metadata-driven scan the delete guards use, so a new foreign key to `product` appears in the preview as soon as its model exists. It rejects the same pairs a merge would (`400` self-merge, `404` per missing side) and, being a read, touches nothing. Preview and merge enumerate the referencing relations through one shared helper, so the counts shown are exactly the rows the merge acts on — they cannot drift apart. They are what the merge *touches*, not what it reassigns: the four configuration relations it deletes are counted too, so a client labelling the whole total "will be reassigned" would overstate it
- SQL migration runner (`uv run python -m app.db.migrate`): applies every migration the target database has not yet received, in numeric-prefix order, and records each one in a `schema_migrations` ledger table inside that database — so what a database has received is a property of the database, not of whoever last ran something by hand. `status` reports applied vs pending; `mark` records a migration as applied without executing it, for changes made before this tooling existed. Statements are split client-side, so a failure names the exact statement, not just the file — which matters because MariaDB does not roll back DDL and a half-applied file needs manual resolution

### Fixed
- **Profit-margin validation compared a price against a rate.** `product_price.low_profit` and `high_profit` are profit *rates* — every one of the 61,855 rows in `mbe_dev` has both between 0 and 1, typically `0.000000` and `1.000000`. The new line-add check compared the raw price against them, so a ₱23.00 price failed `23 > 1`: with `price_validation_in_range_required` on by default, only 734 of 61,855 product-price rows would have passed and 98.8% of the catalogue would have been unsellable. The check is now on the derived margin `(price - cost) / price` against those rates, which is what the columns mean. A zero price is not judged there — confirmation refuses it outright and dividing by it has no meaning. Found by driving a real order through `mbe_dev`; no unit test with invented fixtures would have caught it, because the invented bounds looked like prices
- **Reading a cashier's open cash session raised on legacy data.** `cash_session.end IS NULL` is not unique in practice — two cashiers in `mbe_dev` have three and four sessions open simultaneously — and the lookups used `scalar_one_or_none()`, which raises `MultipleResultsFound`. Recording a payment as either cashier returned a 500. The three affected queries now order by `start` and take one; `open_session` still refuses to *create* a second, so the tolerance only ever applies to pre-existing rows
- `POST /api/v1/products/merge` now moves every reference the duplicate carries, not the six a hand-written list happened to name (#112). Eleven mapped foreign keys were left behind — `sales_quote_detail`, `delivery_order_detail`, `fiscal_document_detail`, `customer_refund_detail`, `purchase_request_detail`, `customer_discount`, `lot_serial_rqmt`, `supplier_return_detail`, `service_order_detail.spare_part`, `commission_product` and `commissions_history` — so deleting the duplicate hit an enforced foreign key and the whole merge rolled back with a generic conflict. In `mbe_dev` that was 13,248 of 21,542 products: any product ever quoted, delivered, invoiced, refunded or requested could not be merged at all. `commission_product` and `commissions_history` are worse — they declare a `ForeignKey` in the model but have no constraint in the database, so those merges *succeeded* and left commission rows pointing at a deleted product (1,008 and 248 products carry such rows). The remap set now comes from the mapped metadata, the same source the delete guards and the merge preview read, so a new foreign key to `product` is covered as soon as its model exists. Verified against `mbe_dev` by merging the product with the most fiscal history (83,488 rows across 13 relations) inside a rolled-back transaction: the delete succeeds and nothing is left pointing at it, where the old path fails on `customer_refund_detail`

A stamped CFDI keeps its own `product_code` / `product_name` snapshot, so what the document says was invoiced is unchanged — only the catalog row it points at moves, and that row is about to stop existing
- A merge moves the duplicate's *history* and discards its *configuration*. The four relations that describe how a catalog row is set up rather than what happened to it — `product_price`, `product_label`, `commission_product`, `customer_discount` — are deleted for the duplicate instead of being reassigned: the canonical is the row being kept, so its own prices, labels, commission assignment and per-customer discounts are the ones that survive. Each of the four has a unique key covering the product column, so the duplicate's rows could never all have landed on the canonical anyway; deleting them outright makes the outcome identical for every row rather than depending on which ones happened to collide. **A label or per-customer discount that existed only on the duplicate is not carried over** — set it on the canonical before merging if it should survive
- Database constraint violations return `409` instead of `500` (#107). Deleting a record that something still references is refused with the blocking `table.column` and row counts named in the error, so a client knows what to clear; the referencing tables are derived from the mapped metadata, so a new foreign key is covered as soon as its model exists. Creating or updating a warehouse, point of sale, cash drawer or vehicle with a duplicate `code` / `license_plate` is likewise `409` rather than `500`. An `IntegrityError` handler backstops anything not checked up front, returning a generic conflict — the driver message is logged, never returned, since it names tables and indexes
